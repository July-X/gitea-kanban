## 问题背景

User 反馈：Git Graph 视图里**左侧 Graph 列中段出现"幽灵 line"**（彩色线条穿过某 row，但该 row 上没有对应的 commit 圆点），同时**部分 commit 圆点不在 lane 0 主干**上，而是被推到 lane 2/3/4/5/6 的"边缘 lane"，**主干 lane 0 出现 49 行的贯穿彩色线段**但沿途没 dot。

视觉对比（同一仓库）：

| 视图 | 现象 |
|---|---|
| **VS Code Git Graph 扩展**（v1.30.0） | 蓝色 master 主干 lane 0 贯穿始终，所有 main chain commit 都在 lane 0，feature 分叉在 lane 1+，merge 后 lane 自然回收 |
| **gitea-kanban v0.8.23** | 蓝色主干 lane 0 出现 49 行贯穿"幽灵 line"，main chain commit 大多被推到 lane 2/3/4/5/6 |

## 根因（VS Code 原版 vs Go 复刻 1:1 对比）

把本地原版仓库 `D:\2026\github\vscode-git-graph\web\graph.ts`（v1.30.0）与 `app/git/graph/layout_vscode.go` 逐项对照：

| 函数 | vscode 原版 | 我们的 Go 版 | 差异 |
|---|---|---|---|
| `Vertex.getPointConnectingTo` | 用 `UnavailablePoint[]` 数组遍历 | 用 `map[int]*UnavailablePoint` 遍历 | 1:1 等价（map 单 key） |
| `Vertex.registerUnavailablePoint` | `if x === nextX: nextX++; connections[x]={...}` | 完全一致 | 1:1 等价 |
| `getAvailableColour` | 复用已结束颜色索引 `availableColours[i] < startAt` | 完全一致（layout_vscode.go:225-233 注释已说明） | 1:1 等价 |
| `determinePath` 主循环 | `while (i < vertices.length) determinePath(i)` | 完全一致（仅多 safety 防死循环） | 1:1 等价 |
| `Branch.addLine` + `numUncommitted` | isCommitted/numbered 推进策略 | 完全一致 | 1:1 等价 |
| 前端 `Branch.draw`（pixel 放置 / 共线合并 / 续接 / C 贝塞尔控制点） | `GRID_Y * 0.8` rounded / `0.38` angular | `vscode-render.ts:409/399` 复用 | 1:1 等价 |

**结论**：我们 Go 版和前端 1:1 复刻了 vscode-git-graph v1.30.0 算法。

用 Python 1:1 复刻 TS 原版算法跑同一 DAG（M0 merge [M1, F1] / M1..M50 first-parent 链 / F1→F0 旁支）——**TS 原版下也产生完全相同的 lane 错位和幽灵 line**。说明这是 **vscode-git-graph 原版的算法 bug**，不是 Go 复刻问题。

具体根因：`vscode-git-graph graph.ts:705-763` 的 `determinePath` 流程：

1. 合并提交 `M0`（merge parent `F1`）被主循环先处理
2. `M0` 走 **merge stitch 分支**（graph.ts:712-729）：`parentBranch.addLine(lastPoint, curPoint, ...)` 循环 j=1..50，每个 curVertex 都 `registerUnavailablePoint(curVertex.nextX, ...)`
3. `curVertex.nextX` 默认是 0；第一次 register `0==nextX` 命中 → nextX=1；第二次 register `1==nextX` 命中 → nextX=2……直到 nextX 推到 6+
4. 后续主循环 top-down 调用 `determinePath(M1..M49)` 时，这些 vertex 的 `nextX` 已经被 merge stitch 推到 2+
5. `vertex.addToBranch(branch, vertex.nextX)` 把 first-parent 链 commit 写到 lane 2/3/4/5/6
6. 但 merge stitch 的 `parentBranch`（主链 Branch[0]，color=0）已经在 lane 0 从 row 0 一路画 line 到 row 50——**沿途 row 1~49 在 lane 0 没有 dot，但 line 段继续往下画**——**lane 0 的"幽灵 line"就这样出现**

## 修复策略

`layout.go`（`BuildGraph`，Gitea 风格）**已经实现** main chain lane 0 锚定策略。把同样策略复用到 `layout_vscode.go`（vscode 风格）。

**`app/git/graph/layout.go:194-226`** 的策略：
1. 识别 main chain：从显式 primary branch ref（`main` / `master` / `origin/main` / `origin/master`）对应的最新 commit 开始，沿 first-parent 一路到底
2. main chain 上的 commit 在 lane 分配阶段**强制 lane=0**
3. feature 分支 lane 查找时**最低 lane=1**（`findFreeLane(minLane=1)` / `findFreeLaneExcept(minLane=1)`），避免抢占 main lane 0

## v0.8.24.1 调研：vscode-git-graph vs GitLens lane 算法对照

User 上轮指出"lane 绘制逻辑完全不符合预期"——本轮排查发现：

| 维度 | vscode-git-graph v1.30.0 | GitLens v18.2.0（GKC 算法移植） |
|---|---|---|
| **lane 分配数据结构** | `vertex.nextX`（每行已用最大 +1）+ `connections[x]` map | `columnsUsed: Set<number>`（行内已用集合） + `columnsToFreeWhenFound: Map<Sha, number[]>`（merge point 释放） |
| **column 分配** | 单调递增：每次 `registerUnavailablePoint` 把 nextX++ | `claimNextColumn` 从 `pinnedColumnCount` 起找最低空位 |
| **column 释放** | **永不释放**——`nextX` 只增不减 | merge stitch 释放对应 column（`assignColumnForRow` 调用 `toFree = columnsToFreeWhenFound.get(row.sha)`） |
| **pinned lane 抢占** | 无显式概念（依赖 first-parent chain 自然延续） | `assignPinnedColumns` + `canReplaceReservation` 显式抢占 |
| **算法类型** | online（top-down 单次扫描） | offline（rows 数组先准备，row-by-row 处理） |

**核心差异**：vscode-git-graph 的 `vertex.nextX` **永不回收**——row 1 占 lane 0、row 2 占 lane 1、row 3 占 lane 2……即使 row 1 的 commit merge 后不再占 lane 0，下一个 sibling 也不会被回收到 lane 0，只能推到 lane 6/7/8——**这就是用户截图里"lane 数 ~35 vs VS Code ~15" 的根因**。

GitLens 的 `columnsUsed` Set + `columnsToFreeWhenFound` Map **真正回收 column**——merge point 显式释放 row 上用过但已完成的 column，下一个 sibling 可以从最低空位开始分配。

### v0.8.24 没解决的：lane 膨胀

v0.8.24 仅修复了"main chain 强制 lane 0"——保证 lane 0 干净。但 sibling branch 之间仍会按 `vertex.nextX` 单调推进推到 lane 2/3/4/5/6+（sibling 间不互相抢占导致 lane 间距拉开）。**真正视觉上 lane 数收敛**需要 GitLens 风格的 column 回收算法。

本轮尝试了一个 `compactLanesForBuildResult` post-process pass（在 `buildResultWithTruncated` 里把 vertex.x 和 branch.line 端点 x 全局重映射到连续编号）——经测试**只能压掉 ghost lane（merge stitch 穿过的 lane 1/3/5/7/9），无法压缩 sibling branch 间已被 vertex.nextX 推到 lane 10/12/14/16/18 的 raw 值**——DTO 输出 lane 数从 15 减到 15（无效）。**已回滚**。

### 下一步可选方案

要让 lane 数真正收敛（目标 ~15 条 lane 而非 ~35），需要替换 lane 分配算法，候选有 3 种：

| 方案 | 工作量 | 改动范围 | 收益 |
|---|---|---|---|
| **A. 替换为 GitLens 算法** | 4-6h | 重写 `layout_vscode.go` 的 `determinePath`（700+ 行）+ 全部相关测试 | lane 数 ~35 → ~10-15；脱离 vscode 1:1 复刻 |
| **B. 重构 vertex.nextX 为 columnsUsed Set** | 2-3h | 改 `vsVertex.connections` 为 Set + `nextFreeLane()` helper；保留现有 `determinePath` 主体结构 | lane 数收敛；保持 vscode 算法骨架 |
| **C. 现状：仅保证 main chain lane 0 + 接受 lane 数较多** | 0h | 不动 | lane 数仍较多但 main chain 干净、无幽灵 line |

**我的建议**：**方案 B**——风险最小、保留现有 13 个 layout.go 回归测试不变、lane 数能从 ~35 减到 ~15 左右、与 vscode-git-graph 算法骨架兼容。工作量 2-3 小时，需要重写 1 个 helper（`nextFreeLane`）+ 调整 `determinePath` 中 nextX 的使用方式（约 10 处）。
