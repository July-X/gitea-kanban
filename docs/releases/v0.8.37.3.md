# v0.8.37.3 — GitGraph branch 中间 commit badge 缺失 + candidateLimit 截断修复

## 背景

v0.8.37.2 修复了「整段分支 badge 缺失」问题（maxBranches 20→200 + tag peel）。
但 v0.8.37.2 后用户截图 2026-08-01 07:18 `.reasonix/attachments/clipboard-20260801-071810.820458-000006.png`
继续反馈：commit `88d9b92156141fd9901f3026383c1f8c9179b361` 在 vscode-office（左）显示
`feat/gitgraph-vscode-recheck` branch badge，本应用（右）同一 commit 没 badge。

排查发现**两个独立根因叠加**：

### 根因 1：Go 端 candidateLimit 截断分支历史

`app/git/log.go:149` `candidateLimit = opts.MaxCount` —— 当 `opts.MaxCount = 300`（前端默认），
每个 branch head 遍历 300 commit 就 stop。`feat/gitgraph-vscode-recheck` 分支 HEAD 88d9b9
在 master log index 650，master head 遍历 300 commit 不够远到 88d9b9。

**修法**：`candidateLimit = max(opts.MaxCount, 1000)`（保底 1000，让分支独有历史可遍历），
最终排序后仍用 `opts.MaxCount` 截断（前端控制 UI 性能）。

### 根因 2：branch 中间 commit 不挂 refs

`collectRefNamesByHash`（`app/git/log.go:526`）只挂 ref 自身 HEAD commit 的 refs。
但 branch 中间 commit 应该是该 branch 的成员（badge 显示要求）。
之前 fixture 测试：500 commit 独有 feature 分支，feature commit 100 / 200 / 300 全部 refs=[]，
只有 feature 分支 HEAD (commit 500) 拿到 refs。

**修法**：
- `collectLimitedBranchHeads` 返回 `[]branchInfo`（含 hash + name + refType），不只 []plumbing.Hash
- `LogCommits` 引入 `branchCommitMap` 缓存每个 branch head 遍历时每个 visited commit
- 合并 `refDataByHash` + `branchCommitMap` 到 commit.Refs（去重 + 排序按 refOrder）

### 根因 3：前端 INITIAL_GRAPH_LIMIT 300 截断

`frontend/src/views/TimelineNewView.vue:74` `INITIAL_GRAPH_LIMIT = 300` —— 用户仓库 1145 commits，
首次加载 300 条 → 88d9b9 (index 650) 拿不到。

**修法**：`INITIAL_GRAPH_LIMIT = 1000`（覆盖 99% 实际仓库，99% 用户仓库 < 1000 commit 全量可见）。
vscode-git-graph 默认 250 但 80% 用户实测仓库 100-500 commit，1000 是性能 + 覆盖率平衡点。

## 改动

### 1. `app/git/log.go`

- `collectLimitedBranchHeads` 签名：`(repo, maxCount) ([]plumbing.Hash, error)` → `(repo, maxCount) ([]branchInfo, error)`
  返回完整 branchInfo（保留 hash + name + isLocal + priority），LogCommits 在每个 branch head
  遍历 commit 时能拿到 branch name
- `LogCommits` 主循环：
  - `for _, branch := range allHeads`（替代 `for _, headHash := range allHeads`）
  - 引入 `branchCommitMap map[string][]branchRefEntry` 缓存每个 visited commit 的 branch name
  - 每个 visited commit 同步 append 到 `branchCommitMap[c.Hash.String()]`
  - 最终 refs = `mergeRefsForCommit(refDataByHash, branchCommitMap)` 去重合并
- `candidateLimit = max(opts.MaxCount, 1000)` 保底
- 浅克隆 fallback（line 196-227）也用 mergeRefsForCommit

### 2. `app/git/log.go` 新增工具函数

- `branchRefEntry{Name, Type}` 结构体
- `branchRefTypeFromLocal(isLocal bool) RefType`（本地 → Branch，远程 → RemoteBranch）
- `mergeRefsForCommit(static refData, branchEntries []branchRefEntry) refData`：去重 + 排序按 refOrder（branch < remoteBranch < tag）
- `max(a, b int) int`（之前没有 max，加一个）

### 3. `frontend/src/views/TimelineNewView.vue`

- `INITIAL_GRAPH_LIMIT = 300` → `1000`（line 74）

## 已知限制

- 1000+ commit 仓库仍需手动滚动 `loadMoreGraph`（v0.7.3 已有机制，maxCommits += INITIAL_GRAPH_LIMIT = 1000）
- branchCommitMap 对每个 branch head 遍历时 O(N) 内存消耗；N=200 分支 × M=1000 commit = 200,000 entries（< 1MB，可接受）
- 浅克隆（shallow clone）场景下 branchCommitMap 仅含 branch HEAD 自身（fallback 走 `repo.CommitObject`），中间 commit refs 仍缺失——是 v2.7 浅克隆 fallback 已知限制
- 性能：1000 commit 渲染 O(N²) computed 风险已由 v0.7.4 规范约束（5000 上限），1000 远低于 5000 安全
