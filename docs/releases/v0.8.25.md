## 问题背景

v0.8.24 修了 vscode-git-graph 原版「幽灵 line」+ main chain lane 错位（具体见 [v0.8.24.md](./v0.8.24.md)），但**lane 膨胀问题没解决**：gitea-kanban 自己的 master 在 8 月份就 ~35 条 lane，视觉过宽。User 期望和 GitLens / GitKraken 桌面端一致的 ~10-15 条紧凑视觉。

实测两个候选 lane 分配算法：

| 算法 | 在真实数据上的 lane 数 | 主链干净度 |
|---|---|---|
| vscode-git-graph v1.30.0（v0.8.24 已修幽灵 line） | ~35 | ✅ |
| GitLens v18.2.0（GKC 算法移植） | ~10-15 | ✅ |

**拍板**：移植 GitLens 算法（细节 + 双轨决策见 [gitgraph-engine.md §0 + §2.2](../design/gitgraph-engine.md)）。

## 改动内容

### 1. 新增 `app/git/graph/layout_gitlens.go`（896 行）

Go 1:1 移植 `vscode-gitlens/packages/plus/commit-graph/src/engine/layout.ts` + `edges.ts`：

| GitLens TS API | Go 移植（layout_gitlens.go） |
|---|---|
| `computeColumnsAndSegments(rows, opts)` | `gitlensAssignColumns(rows, pinnedHeadShas, compact bool)` |
| `columnsUsed: Set<number>` | `state.columnsUsed map[int]bool` |
| `columnsToFreeWhenFound: Map<SHA, number[]>` | `state.columnsToFreeWhenFound map[string][]int` |
| `LaneSegmentBuilder` | `gitlensSegmentBuilder struct` |
| `computeEdges(rows, columns)` | （合并到 BuildGraphGitlens 主循环） |
| `splitLockFirst(line, rowH)`（前端） | `vscode-render.ts:renderBranchLines splitLockFirst` |

5 个算法层函数 vs 内部 helper 共 60+ 个；类型定义 `gitlensGraphRow` / `gitlensReserverInfo` / `gitlensLaneSegment` / `gitlensLayoutState` 见 [§2.1](../design/gitgraph-engine.md#21-关键数据结构layout_gitlensgo25-95)。

### 2. 双轨布局（compact=true 视觉 + compact=false 取色）

GitLens compact 模式运行到 1500+ commits 时会把 lane 编号从 14 → 8 压缩，但**同一 segment 内 commit 在两个 pass 的 lane 不一致** — 颜色按 segment claim 时绑定，不能改。

```go
columns, segments, maxCol := gitlensAssignColumns(rows, pinned, true)   // 视觉紧凑
colorCols, _, _        := gitlensAssignColumns(rows, pinned, false)     // 按 claim 顺序取色
```

性能数据（master laptop 实测）：

| commits | 单遍 | 双遍 |
|---|---|---|
| 100 | < 3ms | < 5ms |
| 500 | < 15ms | < 25ms |
| 1000 | < 35ms | < 60ms |
| 3000（上限） | < 80ms | < 150ms |

### 4. v0.8.25.x 后段：连线形态 1:1 复刻 GitLens（`64499be`）

**最大一轮 fix**，综合 4 处 GitLens 移植遗漏：

| 现象 | 根因 | 修复 |
|---|---|---|
| 分支 lane 无限延伸 | fork stitch 整段缺失（`segmentToLines` 不处理 `seg.forkSha`） | 补 fork stitch（LockedFirst=false） |
| 0b614de → 2ba6605 汇入线数据缺 | pinned parent 汇入时 segment 不 finalize | `assignColumnForRow` else-if 分支标记 `columnsToFreeWhenFound` |
| 1348ba6 → cfcf339 主线蓝斜线丢失 | second parent 已在别 lane 时 branches 里缺边 | 补 merge incoming line 单线 branch |
| merge 边颜色反 | 恒为 child 色 | 改为 parent 链色（被合入方） |
| 跨 lane 长线整条对角线 | 不 pushSplit | 补 `vscode-render.ts:renderBranchLines splitLockFirst` |

**回归测试**：4 个新 Go 测试文件（`layout_gitlens_test.go` / `..._dto_test.go` / `..._e2e_test.go` + `dump_branches_test.go`）共 1318 行覆盖：单元 + DTO 转换 + 真实 TRex 仓库端到端行级对比。

### 5. 配色优化（`1075a95` + `07f3fb6`）

lane 调色板移除红色系：

| commit | 替换 |
|---|---|

## 决策记录

| 决策 | 选项 | 拍板 | commit |
|---|---|---|---|
| 算法选型 | 维持 vscode 原版 vs 替换 GitLens | lane 数从 ~35 → ~10-15 | `5caa347` |
| 双跑还是单跑 | 双跑 visual+color vs 单跑按 segment 首次 claim 取色 | 双跑（性能可接受） | `5caa347` |
| merge edge 颜色 | child 色 vs parent 色 | parent 色（GitLens 原版实测） | `64499be` |
| 跨 lane 长线 | 整条对角线 vs pushSplit | pushSplit + LockedFirst | `64499be` |
| 排序键 | authorDate vs committerDate | committerDate（cherry-pick 行序 bug） | `b989f9f` |
| 配色：lane 1 | 草绿 vs 亮橙 vs 玫红 | 亮橙（实测高对比） | `07f3fb6` |

## 不决事项（留待下个 release 拍板）

- [ ] 是否将 `BuildGraph`（layout.go，Gitea 风格）也切换为 GitLens 输出 + Gitea 风格渲染 — 当前 Gitea 风格仅作 fallback，AI 用户场景大部分已经走 GitLens 算法。
- [ ] `compact=true` vs `compact=false` 调度是否改为「segment 首次 claim 时取色，全图渲染时按 compact 后 lane 找最近 segment claim」单跑方案 — 当 commit 数 > 5000 时启用。
