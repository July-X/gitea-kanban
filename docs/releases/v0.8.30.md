## 问题背景

用户 2026-07-31 反馈另一个绘制 bug：

> "处理这一个点绘制多次 lane 的 bug" —— 用户对单 main 分叉单 PR 仓库的截屏
> （`643 × 144 px` 截图，Kanban demo `m4java-test`，3 个 commit row）：
>
> 1. `Uncommitted changes (2 files)`
> 2. `origin/int-test-1782998137207128000 integration test fixture` —— 1 commit，只它
> 3. `main origin/main Initial commit`
>
> 该 int-test 那条 branch lane（橙色）在前端被画了 **2 次** —— 同一坐标的
> 正向+反向 2 条 SVG path，stroke-width 视觉叠加，看起来"粗了一倍"或者像
> "过度绘制"。

## 根因

`app/git/graph/layout_gitlens.go` 的 `segmentToLines` 函数，给 int-test 这种
**单 commit fresh claim** segment 同时输出了 2 条线：

```
DEBUG: col=1 mergeSha="" branchSha="main_head_sha" forkSha="main_head_sha" commits=1
```

int-test segment 同时设置了 `branchSha = main_head_sha`（来自 assignColumnForRow
line 295-310："fresh claim 从 parent 列拉分支"）和 `forkSha = main_head_sha`（来自
line 369-371："parent 是 pinned head 时释放 lane"）。

`segmentToLines` 走：
- `else if seg.branchSha != ""`（line 595）→ 生成 `(0,2)→(1,1)` line（branch-off 入线）
- `if seg.forkSha != "" && len(seg.commitShas) > 0`（line 659）→ 生成 `(1,1)→(0,2)` 反向 line（fork stitch 汇入线）

两条 SVG path 视觉叠加在同坐标上 = 用户看到的"绘制多次 lane"。

**根因详细**：

v0.8.26.x 修复 fork 缺失时引入了"parent 是 pinned → 释放 lane"的语义（line 369），但
没意识到当父节点是 pinned main head 时，child 的 branch-off 起点也指向同一
main head → **branchSha 与 forkSha 同时存在**。

v0.8.27 改 branchSha = branchCol < firstCol；v0.8.25.3 改单 commit 也画线；
两阶段修复后形成了这个 corner case 触发。

## 方案

在 `segmentToLines` 的 fork path 加入 **自指跳过**：

```go
isSelfRef := seg.forkSha == seg.branchSha ||
    seg.forkSha == seg.tipSha ||
    seg.forkSha == seg.commitShas[0]
if !isSelfRef {
    // ... 原有 fork stitch 生成逻辑
}
```

**跳过条件含义**：
- `forkSha == branchSha`：branch-off 起点与 fork 汇入目标重合 → 是 branch-off 而非 fork
- `forkSha == tipSha`：fork 自己（理论不可能但防御）
- `forkSha == commitShas[0]`：单 commit segment 时 fork 等于该唯一 commit 任一父项
  （branch-off 起点 & fork 汇入目标同时为同一 SHA 的 corner case）

**为何要分三种条件**：fresh claim 单 commit segment 下，`branchSha` 和 `forkSha` 都等于唯一的
parent SHA（int-test 的 parent = main_head_sha）。三条条件同时成立但缺一不可地
捕获这一情形。

**真实场景**：
- fresh claim（如 int-test）只该画 1 条 branch-off line —— 修复保留
- 真正的 fork 汇入（feature branch 末端的合并 commit）—— `forkSha` 通常是
  main head 上某个**后续** commit（与 branchSha 不同），不触发跳过
- merge stitch（merge commit 之后的旁支）—— `mergeSha` 主导，branchSha 和
  forkSha 通常为空，不触发跳过

预期回归：所有"已合并 PR 末端的 feature 分支 commit 上的 fork stitch"测试
应继续通过，因为这些场景下 branchSha 跟 forkSha 不重合（branchSha 是分支起点
祖先，forkSha 是分支终点合并目标）。

## 改动内容

### 1. `app/git/graph/layout_gitlens.go`：segmentToLines fork path 自指跳过

`if seg.forkSha != "" && len(seg.commitShas) > 0` 内部增加 `isSelfRef` 检测，
跳过 `forkSha` 与 `branchSha` / `tipSha` / 第一个 commit SHA 重合的
corner case，避免生成与 branch-off 反向的重复 fork stitch line。

最小 diff：增加 4 行 if 检查 + 嵌套层级 1 层。无其他逻辑改动。

### 2. `app/git/graph/layout_gitlens_dto_test.go`：回归测试

- 复刻用户截图拓扑（UNCOMMITTED + int-test + main HEAD）

- 核心断言：每 branch 内部 (X1,Y1,X2,Y2) 四元组唯一（修复前 1 个 4 元组

## 风险与权衡

- **真 fork 场景回归风险**：low。真实 fork 是 feature branch 末端的合并 commit，
  `branchSha` 是分支祖先（远离 forkSha），不会触发跳过
- **多 commit segment**：`commitShas[0]` 仍可能等于 `branchSha`（首 commit 是
  branch-off 起点）但 `forkSha` 必须等于内部某个 commit（不是自己）——修复
  不影响
- **未 commit + 单独 commit 的混合**：如 UNCOMMITTED + int-test + main_head
  会触发本修复场景（实测）—— 单 commit segment 必须走这路径
