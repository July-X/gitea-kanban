# v0.8.36 — GitGraph 算法对标从 vscode-gitlens 切到 vscode-office（后端算法层）

## 背景

CLAUDE.md 长期记录 v0.8.25~v0.8.35 一直在对标 `vscode-gitlens`（`packages/plus/commit-graph/src/engine/layout.ts` GKC 算法）。但用户的真实对标意愿是 `vscode-office`（`src/react/view/gitHistory/graph/layoutEngine.ts` 455 行 Branch/Vertex/Line 范式）—— 之前的 gitgraph-engine.md 文档与现实工作目标不一致。本次 commit 仅做**后端算法层切换**，前端 UI 仍走现有 `vscode-render.ts`（独立 commit 处理）。

## vscode-gitlens vs vscode-office 范式差异

| 维度 | vscode-gitlens（v0.8.25 起） | vscode-office（v0.8.36 起） |
|---|---|---|
| **lane 数据结构** | `state.columnsUsed: Set<int>` + `state.columnsToFreeWhenFound: Map<SHA, int[]>` | `vertex.connections: Map<int, Connection>` + `vertex.nextX` 单调游标 |
| **column 分配** | `state.claimNextColumn()` 从 `pinnedColumnCount` 起找最低空闲 | `vertex.getNextPoint()` 沿用 office 简单 `nextX++` 累加 |
| **颜色回收** | `availableColours[i] > startAt` 简单判断 | `Column 释放`清晰（branch.end 设定 + new branch 重用 colour） |
| **merge stitch** | `visitPath` 状态机 + `mergeSha` 锚点 | `determinePath` 沿 column 找 `getPointConnectingTo` 命中点斜切 |
| **代码规模** | 871 行 Go（layout_gitlens.go） | 479 行 Go（layout_office.go）/ 455 行 TS（layoutEngine.ts） |
| **side effect** | ghost line 修复（v0.8.24）+ lane 压缩坑（v0.8.33 fix） | 单一简单类，bug 维度少 |

vscode-office 风格跟 vscode-git-graph v1.30.0 原版几乎一致（layoutEngine.ts 注释反复写 `graph.ts:50-60`、`graph.ts:75-147` 等行号对齐），但跟 vscode-gitlens 范式有本质差异。两者**不是同一类算法** —— 切对标仓库是切换实现范式，不是同范式下换个 implementation。

## 改动

### 新增 `app/git/graph/layout_office.go`（479 行）

业务目标：1:1 移植 `vscode-office/src/react/view/gitHistory/graph/layoutEngine.ts` 到 Go，输入 `[]git.CommitInfo` 输出 `*GraphResult`（复用现有 DTO，前端 `vscode-render.ts` 不动）。

**核心类**（跟 TS 原版对齐）：

- `officeVertex`（对齐 `Vertex` class）：id + isStash + x + children + parents + nextParent + onBranch + isCommitted + isCurrent + nextX + connections[]，含 `addParent` / `addChild` / `getNextParent` / `registerParentProcessed` / `isMerge` / `addToBranch` / `isNotOnBranch` / `getPoint` / `getNextPoint` / `getPointConnectingTo` / `registerUnavailablePoint` / `getColour` / `setNotCommitted` / `setCurrent` / `toRenderData`。
- `officeBranch`（对齐 `Branch` class）：colour + lines[] + end + numUncommitted，含 `addLine` / `getColour` / `getEnd` / `setEnd` / `toPaths`。
- `officeGraphEngine`（对齐 `GraphEngine` class）：vertices[] + branches[] + availableColours[] + onCurrentBranch[]，含 `compute` / `determinePath` / `getAvailableColour`。

**算法核心 1:1 复刻**（`layoutEngine.ts:267-432`）：

- `determinePath(startAt)` 两分支：
  - merge stitch（line 373-393）：merge vertex 已挂 branch 且 parent 也挂 branch 时，沿 column 找 `getPointConnectingTo` 命中点斜切
  - new branch（line 394-422）：开新 Branch + 沿 parent 走到底
- `getAvailableColour(startAt)`（line 425-431）：回收 `availableColours[i] < startAt` 的颜色槽位
- `Vertex.registerUnavailablePoint`：`nextX` 单调累加
- `Branch.addLine`：`numUncommitted` 维护规则（committed=true + p2.x=0 + p2.y<numUncommitted 时推进；否则 ++）
- 主循环（line 331-338）：vertex 有 nextParent 或 notOnBranch 时 `determinePath(i)`，否则 `i++`

**死循环保护**（Go 版特有）：office TS 原版主循环假设 `commits[]` 按时序倒序（head 在 row 0）+ parent row > child row。如果外部传入乱序，主循环会死循环（TS 里有调用栈溢出兜底，Go 里没有）。Go 版加 `prevNextParent != nil && prevOnBranch == nil` 进度判定：determinePath 返回时 vertex 没消费 nextParent 也没挂 branch → `i++` 跳过，避免死循环。

**DTO 转换层**（同文件内）：

- `Nodes[i].Lane = officeVertex.x`，`Color = Lane % 16`（对齐 Gitea Color16 + 现有 gitlens 路由）
- `Edges[i].Color` 跟 gitlens 现行一致（merge 边用 parent 色），`Type = EdgeNormal/Branch/Merge` 由 lane 差决定
- `Branches[i].Lines[i].IsCommitted = (lineIndex >= numUncommitted)`
- `MaxLane = max(vertex.x)`，`MaxColor = 16`，`Truncated` 透传

**pinned head 兜底**：跟 `BuildGraphGitlens` 一样兼容 `pinnedHeadShas` 入参（虽然 office 算法只用 `commits[0].SHA` 当 head，但接口签名一致以便 adapter 一键切换）。

## 已知风险

1. **算法切换视觉差异**：office 走 `vertex.nextX` 单调游标（vscode-git-graph v1.30.0 原版），gitlens 走 `columnsUsed` Set 真正回收。深历史仓库（>300 commit，旁支密集）实测会有 lane 差异（office 偏左、gitlens 偏右平均分配）。**需要用户层面真仓库验证**确认是否符合预期。
2. **color 维度**：office 走 `branch.getColour() % 16`（branch end 后的颜色回收），gitlens 走 `colOf[sha] % 16`（SHA → column 映射）。两条路径在常见 DAG 上等价，但极端拓扑（如 16+ 同时活着的 branch）会有细微差异。
3. **乱序输入死循环保护**：实测真实 git log 倒序不会触发。但子代理测试中构造乱序 fixture 时发现 office 主循环潜在死循环——已加 `prevNextParent` / `prevOnBranch` 进度判定兜底。
