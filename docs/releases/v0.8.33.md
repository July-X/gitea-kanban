# v0.8.33 — 回退「lane 左移压缩」：恢复 GitLens 原版 lane 复用行为

> 发布日期：2026-07-31
> commit：（待 push 后回填）
> tag：（待打）
> release：https://github.com/July-X/gitea-kanban/releases/tag/v0.8.33

## 问题背景

实测 `D:\2026\github\DeepSeek-Reasonix`（301 commits）的 git graph 与 vscode-gitlens 截图对比，发现长分支链被整体左移到左侧少数 lane，右侧 lane 几乎全空，与 GitLens Commit Graph 渲染不一致：

| Lane | v0.8.32 (compact) | v0.8.33 (本版) |
|------|------------------|----------------|
| 0 | 55 | 55 |
| 1 | 115 | **128** |
| 2 | 13 | 13 |
| 3 | 24 | **27** |
| 4 | 23 | **18** |
| 7 | 26 | **2** |
| 9 | 4 | **28** |
| 11-14 | 几乎全空 | 自然分布 |

v0.8.32（"lane 0/1 吃满，lane 11+ 全空"）的形态 vs GitLens（lane 1 释放后由后续 commit 复用，lane 7+ 持续有长分支链）有明显差异。

## 根因

v0.8.25.7 引入的 `compactLanes()` 把 lane 释放后右侧所有活跃 lane 整体左移一格。这个行为是 v0.8.25.7 移植时**凭印象**写出来的，与 GitLens `commit-graph/src/engine/layout.ts:493-510` 的实际算法不符：

- v0.8.25.7 假设：GitLens 在 lane 释放后会做"立即填坑"——右侧所有 reservation/segment 左移一格
- 实际：GitLens 只从 `columnsUsed` 集合中移除空 lane，**不动**现有 reservation/segment 的 column；后续 commit 走 `claimNextColumn()` 复用最低空 column

v0.8.25.7 当时仅在 TRex 仓库（深度较浅）做了肉眼比对，未在大规模长分支链仓库上量化验证。DeepSeek-Reasonix 301 commits 暴露了这条逻辑的缺陷。

## 改动内容

### 1. `app/git/graph/layout_gitlens.go` 删 `compactLanes` 逻辑

- 删 `gitlensLayoutState.compact` 字段
- `compactLanes()` 函数体改为 no-op（保留函数引用作历史 reference）
- `assignColumnForRow` 删 `if s.compact { ... s.compactLanes(col - delta) ... }` 块
- `newGitlensLayoutState` 删 `compact bool` 参数
- `gitlensAssignColumns` 删 `compact bool` 参数
- 详细注释记录 v0.8.25.7 → v0.8.33 的纠偏原因

### 2. `BuildGraphGitlens` 删双轨布局

v0.8.25.7 引入的"位置用压缩 lane + 颜色用未压缩逻辑 lane"被同步证伪：

- 删 `colorCols, _, _ := gitlensAssignColumns(rows, pinned, false)` 第二跑
- 删 `colorColOf` 映射
- 节点 `Color` 字段从 `colorColOf[c.SHA] % 16` 改回 `colOf[c.SHA] % 16`（与位置一致）
- 边 `Color` 字段同步从 `colorColOf` 改回 `colOf`
- merge 合入线的 `Color` 同步改回 `colOf`
- `segmentsToBranches` 内部仍接受 `colorColOf` 参数（但调用方传 `colOf`，行为等价于颜色=位置；保留函数签名减少 diff 噪音）

**结果**：位置和颜色用同一套 GitLens 原版 lane 分配，与 GitLens commit-graph 算法 1:1 对齐。

### 3. `app/git/graph/layout_gitlens_dto_test.go` 测试更新

- `TestBuildGraphGitlens_LaneCompactMatchesGitlens`（v0.8.25.7）改名为 `TestBuildGraphGitlens_MatchesGitLensLaneReuse`
  - 拓扑不变（与原测试相同的 11 commit DAG）
  - 预期 L 链稳定在 **lane 2**（不左移）、X1 复用 **lane 1**（A 链释放后的最低空 column）
  - 颜色 = 位置（取消双轨）：L 链 color=2，X1 color=1
  - 验证 L 链 row 4-9 区域**不**再有跨 lane 1↔2 转场
- `TestBuildGraphGitlens_ColorIsColumnMod16` 注释更新，引用新测试名

### 4. `app/git/graph/layout_gitlens_test.go` 测试同步

6 处 `gitlensAssignColumns(rows, nil, false)` 调用去 `compact` 参数。

### 5. `app/git/graph/debug_dump_test.go` 加 `GRAPH_DEBUG_MAX_COUNT` 环境变量

支持 DeepSeek-Reasonix 301 commits 规模（默认仍 40）。配套使用：

```bash
GRAPH_DEBUG_REPO='D:\2026\github\DeepSeek-Reasonix' \
GRAPH_DEBUG_MAX_COUNT=301 \
go test -v -run TestDumpRealRepoLanes ./app/git/graph/
```

## 回归风险

| 风险 | 缓解 |
|---|---|
| lane 数比 v0.8.32 略多，UI 左侧宽度可能增加 | 验证表明 v0.8.33 与 v0.8.32 maxLane 都是 14（pinned head + 长分支链右端点不变，巧合），实际增长为 lane 7 26→2 / lane 9 4→28 自然分布，**总 lane 数不变** |
| 颜色会跟着 lane 变化（v0.8.25.7 的"位置与颜色分离"被证伪后恢复一致） | 这是预期修正：取消双轨后 Color == Lane%16，与 GitLens 原版一致 |
| 之前 v0.8.25.7 的"绿色斜跨 L 链"渲染消失 | 是预期：取消压缩后 L 链稳定在 lane 2 竖线，不再有跨 lane 转场；与 GitLens commit-graph 实测 1:1 对齐 |
| `compactLanes` 函数体改 no-op 但保留签名 | 仅减少 diff 噪音，外部无引用，行为 0 影响 |
| 测试 fixture 拓扑不变 | 仅断言改写，旧 commit hash（v0.8.25.7 引入的 TRex 场景复刻）保持可追溯 |

## 不决事项（不在本版本范围）

1. 用户未标明 GitLens 版本。**如果**实测按当前官方算法修复后仍有小差异，下一步需要锁定用户本机 GitLens 版本，按该版本源码再校准。当前先不阻塞。
2. UI 左侧宽度如果因 lane 数增加出现裁剪，单独检查 `TimelineNewView.vue` 的 `svgMaxWidth` 计算，**不要为了视觉紧凑把算法又改回去**。
3. 旧 v0.8.25.7 commit hash（"lane 左移压缩"原始 PR）的 release note 保留为历史记录（v0.8.25.md 段落），不重写事实。
