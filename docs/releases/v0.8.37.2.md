# v0.8.37.2 — GitGraph 后端「分支 badge 缺失」修复（maxBranches 20→200 + tag peel）

## 背景

用户截图 2026-08-01 06:52 `.reasonix/attachments/clipboard-20260801-065240.009861-000004.png`
+ `clipboard-20260801-065303.363345-000005.png` 显示 Git Graph 整段分支 badge 缺失：

- 图一（应用当前样式）：badge「feat/gitgraph-vscode-recheck」可见
- 图二（同 commit 行）：该 badge 缺失

排查发现 2 个独立根因叠加导致，按可能性排序：

### 根因 1：`maxBranches = 20` 硬切（v2.7 引入）

`app/git/log.go:332` `collectLimitedBranchHeads` 最多遍历 20 个分支 head。

- 仓库分支数 > 20 时，第 21+ 个分支的 head commit **完全不会进入 commits 列表**
- `collectRefNamesByHash` 维护全量 `map[SHA]refData`（不管 20 上限），但 commit 本身缺席 → 前端 `r.commit.refs` 渲染列表时该 commit 不存在 → 不只是 badge 缺失，**整段分支的所有 commit 行都不显示**
- 注释原文：「超大仓库（如 UnrealEngine）可能有几十上百个分支，全遍历会非常慢」—— 20 上限的动机是有，但副作用延伸到了常见 20-50 分支仓库

### 根因 2：Gitea 链路 annotated tag 不 peel

`app/git/log.go:568`（修复前）`sha := ref.Hash().String()` —— 对 annotated tag 返回 **tag object hash** 而非 **commit hash**。

- `byHash[sha]` 挂到 tag object hash 上，commit 永远查不到这个 tag
- GitHub 链路 `listRefsByCommit`（`app/git/ascii_graph.go:268`）用 `git for-each-ref ... %(*objectname)` 早已 peel 对齐
- 后果：annotated tag 永远挂不到 commit → badge 缺失（lightweight tag 直接指 commit 没 peel 问题）

## 改动

### 1. `maxBranches` 20 → 200

`app/git/log.go:332` `const maxBranches = 200`（v0.8.37.2: 20 → 200 修分支 badge 缺失）。

覆盖 99% 实际仓库（普通 monorepo 也最多 50-100 分支），保留兜底防极端仓库性能退化。每个 head 仍受 `candidateLimit = opts.MaxCount` 限制（log.go:149-154），单分支不会全量扫。

行 478-486 的小 maxCount 限制 `min(10, maxBranches)` 保留 —— 小请求（MaxCount < 50）下 10 个 head 已足够。

### 2. Gitea 链路 annotated tag peel

`app/git/log.go:576-585` 新增 9 行 tag peel：

```go
sha := ref.Hash().String()
if refType == RefTypeTag {
    if tagObj, err := repo.TagObject(ref.Hash()); err == nil {
        sha = tagObj.Target.String()
    }
}
```

容错：tag object 解析失败（罕见）退回 `ref.Hash()` 轻量语义。`repo.TagObject()` 是 go-git 的官方 API，对齐 GitHub 链路的 `%(*objectname)` 语义。

## 已知限制

- GitHub 链路的 `listRefsByCommit` 早就有 peel（`%(*objectname)`），本次只补 Gitea 链路
- `maxBranches = 200` 是工程权衡（v0.8.37.2 注释里写明动机）；极端仓库（>200 分支）仍会被截断，但每 head 自身 candidateLimit 兜底
- 浅克隆（shallow clone）场景下 `repo.Log()` 迭代器仍可能失败（log.go:196-220 已有 fallback 处理），peel 改动不触及该路径
- 200 上限对 UnrealEngine 级别（几千分支）仓库性能仍可能退化，但当前数据 99% 仓库在 200 内
